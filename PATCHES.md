# Maintained patches on top of upstream Syncthing

This file is the inventory of the patches this fork carries. It lives on the
fork's `main` branch, which is assembled from the per-patch branches listed
below. See `FORK.md` for how the fork is maintained and rebased.

Upstream tracking issue: https://github.com/syncthing/syncthing/issues/10921
(presents the six headline changes with measurements; PRs offered one per
patch if upstream wants them).

Patches are ordered in dependency order. Each `patch/NN-*` branch contains
everything in the branches before it plus its own piece, so
`git diff patch/NN-1-... patch/NN-...` shows exactly one piece.

| 24 | `patch/24-ring-log-sink` | Logcat-style logging: a fixed in-memory ring (32k lines, `STLOGRINGLINES`) is the primary sink and producers never touch the file; one drainer goroutine performs all output I/O, emitting a gap marker with the drop count if the ring wraps past its cursor. | 25 | `patch/25-monitor-reexec-path` | The monitor re-execs the invocation path, not `os.Executable()`'s resolved target: a stable `current` symlink plus `POST /rest/system/restart` upgrades the binary in place. Deploys become scp + symlink swap + one POST. | 1 |
| 26 | `patch/26-log-traps` | Log traps: arm a filter at runtime (`POST /rest/system/logtraps`) and when a matching line enters the ring, the trap dumps the ring (the recent past), elevates named packages for a window (the verbose future), dumps again at close, and restores levels. Matcher is substring-first (`strings.Contains` — operations and paths are plain substrings in our flat line format) with a RE2 regex escape hatch (linear-time, non-exploitable); the logging package's own lines are exempt so traps can't self-trigger. Runtime-only, zero overhead when nothing is armed. | 1 |
| 27 | `patch/27-concurrent-deletions` | Deletions no longer wait for the pull pipeline to drain: the need walk collects the block hashes of every queued pull, and only deleted files whose local blocks intersect that set (block-reuse sources for in-flight pulls) are deferred to the post-drain pass. All other deletions run concurrently with the pulls. A delete wave arriving during a large pull round (old browser checkout deleted while the new one pulls) applies immediately instead of queueing behind the whole round. | 1 |
| 28 | `patch/28-sqlite-page-cache` | Explicit SQLite page-cache budget per pooled connection (DSN-level, so late-opened connections get it too): 256 MiB total split across the pool by default, floor 8 MiB, tunable via `STDBPAGECACHEMIB`. The 8 MiB SQLite default thrashes a multi-GiB folder DB on slow storage — yarlung's post-restart need scan ran at ~400 rows/min at 1% CPU, all I/O wait on an 8.8 GiB DB (spinning disk), every row costing three random join probes plus a `GetDeviceFile` point lookup. The cache grows on demand, so small databases pay nothing. | 1 |
| 29 | `patch/29-deletes-before-queue` | patch/27's follow-through: the deletion pass started after `processNeeded` returned, but `processNeeded` includes the queue-pop loop that hands every queued pull to the copier pipeline, throttled by fetch rate — so a delete wave still waited behind the whole round (observed live on yarlung: puller parked in the queue loop with 88k deletes pending). Now the walk performs the deferral split, the deletion goroutine starts immediately, and `processQueue` feeds pulls concurrently; rename sources are deferred via block-list-hash match (covers the zero-block case that per-block overlap misses) and consumed from the deferred set. Regression test: the fake remote withholds a block until the deletion lands on disk. | 1 |
| 30 | `patch/30-collapse-abort-logging` | patch/22's collapse verification aborted silently: the first live firefox-tree delete fell back to ~88k per-file deletes with `verifyFailed=1` and no clue why. `verifyDeleteTreeCovered` now returns the first offending path plus a reason (`on disk but not deleted this round`, `unknown to the local index`, `on-disk residue from an earlier failed delete`, `unscanned local modification`, ...) and the caller logs both. Observability only; the verification semantics are unchanged. | 1 |
| 31 | `patch/31-collapse-covers-deferred` | Found by patch/30 on the first live firefox delete: the aborting entry was `.git/hooks/applypatch-msg.sample`, a tiny git sample file byte-identical across checkouts, so patch/29 had deferred it as a rename source for the incoming fresh checkout — and the collapse verifier read "not in this round's deletion set" as user content, abandoning all ~88k deletes to the per-file path. Deferred entries now count as covered (they are deleted later the same round; the collapse merely takes them slightly early, the rename consumer falls back to fetching, and the deferred pass tolerates the file already being gone). One deferred file in a tree no longer blocks that tree's collapse. Regression test: a tree whose one deferred file collapses with it. | 1 |
| 32 | `patch/32-collapse-covers-residue-dirs` | Found by patch/30 on the second live pass: an interrupted deletion pass (restart mid-flight) leaves directories on disk whose tombstones were already consumed — the index says deleted, but the rmdir never happened. Such residue aborted the collapse of the whole tree as "not deleted this round". A directory whose local index entry is already deleted now counts as covered: removing it with the tree is safe because the walk still descends and verifies every entry inside individually, and leaving it would resurrect the empty directory at the next scan. Files stay conservative (content cannot be verified against a tombstone). Regression test: a residue directory collapses with its tree without a duplicate index update. | 1 |
| 33 | `patch/33-collapse-skips-pull-trees` | Composition corner of 22+27+29 found by adversarial review: a pull queued or in flight *under* a collapse root (multi-device inconsistency — tree deleted on one device, an entry inside alive on another, as the live uikit case showed) would have its freshly written or renamed file destroyed by the RemoveAll. The collapse now skips any root the job queue touches (`ContainsPathUnder` over queued + in-progress names; membership only shrinks after the need walk, so one check per root is sound). The per-file path converges safely for those trees. Regression test: a queued pull under the tree skips the collapse until the queue clears. | 1 |
| 34 | `patch/34-wal-autocheckpoint` | One layer of yarlung's write amplification (later measurement showed it was the smaller one — see 35 for the dominant layer): the SQLite default WAL autocheckpoint (1000 pages, ~4 MiB) forced frequent checkpoint flushes of random pages into the 9.3 GiB folder DB, each page CoW-amplified by btrfs; the WAL was observed pinned at exactly 8,388,608 bytes with zero size transitions at 0.2s sampling, wrapping in place at its high-water mark. The threshold is now 262144 pages (1 GiB at 4 KiB pages) on every pooled connection, tunable via `STDBWALAUTOCHECKPOINTMIB`; checkpoints become rare and amortize thousands of commits each. Post-deploy verification: WAL grows normally (183 MiB and accumulating), a passive checkpoint reports `0|27919|27919` (fully checkpointed, no reader pin). modernc takes the setting via `_pragma` DSN (with `journal_mode(wal)` moved ahead of it — the pragma is silently ignored on a non-WAL connection); mattn v1.14.52 supports neither `_wal_autocheckpoint` nor `_pragma`, so the cgo build registers its own driver with a `ConnectHook` applying the pragma per connection. Tests: default/override/invalid parsing, live `PRAGMA wal_autocheckpoint` assertion on both drivers. | 1 |
| 35 | `patch/35-syncfs-batch-durability` | Root cause of the remaining write amplification after 34: on btrfs each fsync forces a log-tree commit costing ~0.8 MB, and a small-file pull stream issues ~2 fsyncs per file (temp file + parent dir). Measured on yarlung: 444 files/min at ~22 KiB (10 MB/min payload) → 550 MB/min of block writes, io pressure >40%, `copiers=8` strictly worse (fsync storm). Linux pulls now sync once per database batch via `syncfs(2)` on the folder filesystem (≤2s cadence, covers temp contents + renames + dir entries), skipping per-file temp fsyncs; durability ordering unchanged (storage sync before index commit; crash residue re-pulls). Falls back to per-dir fsyncs on syncfs error; `STSYNCMODE=fsync` or `DisableFsync` restores old behavior; non-Linux/non-local fs unaffected. Tests: gating and selection (incl. fallback) on both paths. | 1 |
| 36 | `patch/36-db-nocow-auto` | Automates the manual `chattr +C` operators apply to the index directory on CoW filesystems: at database open, `statfs(2)` detects btrfs/bcachefs and `FS_IOC_SETFLAGS` applies `FS_NOCOW_FL` to the directory (before open, so database/WAL/shm inherit at creation) and to an existing database file. Two live findings baked in: `FS_IOC_SETFLAGS` needs `IoctlSetPointerInt` (value-passing returns EFAULT), and btrfs silently ignores NOCOW on files with extents — so pre-existing database files keep CoW until recreated (the code verifies the flag after setting and only claims success when it sticks; the WAL/shm, recreated each cycle, inherit NOCOW from the directory regardless). NOCOW implies NODATASUM for new writes — the same tradeoff as the manual `chattr +C`; `STDBNOCOW=0` keeps CoW and checksums. Best effort: failures log, never block open. Tests: magic detection table, best-effort behavior on any platform; live-probed on yarlung's btrfs. | 1 |

## Measured results

All numbers from this fork's own logs and instruments, on the production
workload: the local Mac's home tree (2.38M files, 394k directories,
262 GiB) mirroring to the remote Linux receiver (Ubuntu, BTRFS RAID1 on
HDD) over WAN. "Before" is stock upstream v2.1.x on the same machines.

| What | Before | After | Patch(es) |
|------|--------|-------|-----------|
| Boot after 5.8 h offline (Mac) | ~40 min full scan | 6 s journal replay (4.17M events) | 05, 14 |
| Scan of the full tree (Mac) | baseline | −40 % wall time | 01 |
| Watcher cost under event storms | fseventsd 104–110 % CPU, 9–19 GB RSS, drop-flag heals adding more load | 0.2–3 % CPU, 14–16 MB RSS; 11,877+ poll cycles, zero drops | 08, 14 |
| First scan on the remote receiver after reboot | ~14–45 min full walk of HDD RAID | snapshot diff, seconds (when a baseline is paired) | 06, 07, 13, 16 |
| End-to-end change latency | watch-driven when the watcher survived; under storms the watch dropped events and healed with scans | 10–23 s stable under storm load, deletes included | 04, 08, 14 |
| Need-list queries (out-of-sync view, pull queue) | full-table scans per query (upstream reporter: 40.5 s median file iteration on a large tree) | maintained need tables; remaining iteration via `files_needed` partial index (reporter: 1.3 s) | 03, 10, 17 |
| GC on 45.5M-row blocks table | single 5-min+ transaction, interrupted, flag lost | per-chunk commits, interrupt-safe, no lock held across | 02, 11 |

## Not included in the clean chain

The deployed history (`feature/btrfs-scan-replay`, kept as the ops archive
branch) additionally contains: temporary debug instrumentation (two commits
marked TEMPORARY), the STGUISTATELOG UI-correlation hook, binary artifacts of
every dev build under `tmp/`, and the incident/deployment ops log. Those are
intentionally absent from `main` and the `patch/` branches.
