# Maintained patches on top of upstream Syncthing

This file is the inventory of the patches this fork carries. It lives on the
fork's `main` branch, whose history is upstream plus every patch's commits
as one contiguous, in-order segment per patch. See `FORK.md` for how the
fork is maintained and rebased.

Upstream tracking issue: https://github.com/syncthing/syncthing/issues/10921
(presents the six headline changes with measurements; PRs offered one per
patch if upstream wants them).

Patches are ordered in dependency order. Each patch's commits sit
consecutively in `main`'s history and carry the `patch/NN:` subject
prefix (history rewritten 2026-10-24 to apply it retroactively; tree
unchanged), so any single patch is extractable as its segment. (The
per-patch branches that used to mark the boundaries were retired
2026-10-21.)

## How to read this

Each row below is one observed problem and one shipped answer. Problem and
Effect stand independently of the mechanism; alternatives that solve the same
problem are legitimate discussion — the numbers are the argument, not the
code. Measured numbers come from the machine constants below; derived
arithmetic is marked with ≈. The two production machines:

(measured 2026-10-24)

Method: cache-bypassed reads on the live folder databases (Mac 8.1 GiB, yarlung 9.7 GiB), temp-file writes in the database directory, 2000-sample random reads, 200-sample fsync loop. All patch impact calculations in this document derive from these constants.

| | **Mac** — MacBookPro18,2, M1 Max 10-core, 64 GB, NVMe/APFS | **yarlung** — Ivy Bridge 4C/8T (2012), 15 GB, 2×7200rpm RAID1, btrfs |
|---|---|---|
| Sequential read | 9.9 GB/s (the 8.1 GiB DB is fully RAM-resident) | 150 MB/s |
| Sequential write + fsync | 2.2 GB/s | 95 MB/s |
| Random 4K read, p50 | 2 µs (warm cache) | 6.7 ms (cache dropped — a real head seek) |
| fsync of a 4K write, p50 | 36 µs | 58 ms (btrfs log-tree commit) |

The asymmetry in one line: a random database touch costs **~3000×** more on yarlung, a durability point **~1600×** more. Every patch below exists because of one of those two ratios.

## The patches

Each row is one *observed problem* and the answer we shipped for it. The Problem and Effect paragraphs stand on their own: they describe what was wrong and what measurably changed, independently of the mechanism. If a different approach solves the same problem (or the same set of problems), the measurements are the shared ground for comparing them — the numbers are the argument, not the code.

| Patch | Problem / Principle / Details / Effect | Relations |
|-------|----------------------------------------|-----------|
| **01**<br>`skip-mtime-on-exists` | **Problem.** Every existence check during a scan paid a virtual-mtime database lookup whose result was never used — 2.38M lookups per full scan. A lookup costs one page read: 2 µs when the page is in RAM, 6.7 ms when it must be sought from disk (machine constants above). Per full scan that is ≈5 s warm, up to ≈4.4 h cold.<br><br>**Principle.** Don't pay for information you don't use: an existence check needs no mtime.<br><br>**Details.** `LstatExists` bypasses the mtimefs lookup through the whole wrapper stack; each wrapper ordering (case-fs, log-fs, walkfs) has its own test.<br><br>**Effect.** Mac (documented in [#10909](https://github.com/syncthing/syncthing/issues/10909)): on stock v2.1.5 the deleted-and-ignored pass alone sat in `GetMtime` for 1 h 44 min without finishing, pulls starved behind it; with the fix the full scan completes in 6–9 min. yarlung: a cold full-tree existence pass drops ≈4.4 h of seeks to zero for this cost class; full scans there are rare anyway since patch/06. | [#10909](https://github.com/syncthing/syncthing/issues/10909) — filed by us with these measurements, closed as not-planned 2026-10-15. |
| **02**<br>`gc-chunked-commit` | **Problem.** Orphan-block GC ran as one transaction across a 45.5M-row blocks table; on a multi-GB index it aborted after 5 minutes, leaving a huge WAL and only a few chunks done — the next run started from zero. Each retry paid the same 5 minutes.<br><br>**Principle.** Long work belongs in bounded chunks that commit and release; interruption then costs at most one chunk.<br><br>**Details.** GC commits per hash-range chunk; blocklist hashes are retired when the block index updates instead of in a full GC scan; the needs-full-scan flag survives an interrupted GC.<br><br>**Effect.** GC completes incrementally and resumes after interruption instead of restarting. No wall-time comparison recorded — the measured fact is structural: 5-minute aborts with zero progress are no longer possible. | [#10868](https://github.com/syncthing/syncthing/issues/10868) — frequent GC with many small files; fixed for ourselves. |
| **03**<br>`need-list-perf` | **Problem.** Need queries (what does the peer lack?) re-ordered and re-computed results on every call — SQL name-ordering plus uncached remote need lists over a 2.38M-row table. On a cold yarlung, each uncached index page is a 6.7 ms seek.<br><br>**Principle.** Cache what is expensive to recompute; order only when a consumer needs the order.<br><br>**Details.** No SQL name ordering in need queries; cached remote need list; cached per-device need count; iterator cost accounting so regressions are visible.<br><br>**Effect.** Need views answer from cache instead of rescanning the table per call. The remaining cold iteration cost is covered by patch/17's partial index (upstream reporter's numbers on a large tree: 40.5 s median → 1.3 s). | — |
| **04**<br>`chunked-scan` | **Problem.** A full scan monopolized the folder's Serve loop for its whole duration: pulls and watch events queued behind the walk. Concretely: the #10909-era scan held the loop for 1 h 44 min with `needFiles=2` waiting, and on yarlung a full-tree walk is 14–45 min even on a good day.<br><br>**Principle.** Break the monolithic walk into timer-budgeted chunks and service queued work at the boundaries; a resumable scan can always pause.<br><br>**Details.** Resumable walks, timer-enforced chunk budget, pull/watch servicing between chunks and during the deletion sweep; tests hardened for CI runners.<br><br>**Effect.** End-to-end change latency stable at 10–23 s under storm load, deletes included (shared measurement with 08/14); pulls no longer wait out a full walk. | Watching [#10264](https://github.com/syncthing/syncthing/issues/10264) (SQLite at scale — same wall, different attack); [#8418](https://github.com/syncthing/syncthing/issues/8418) adjacent. Compare [#10516](https://github.com/syncthing/syncthing/pull/10516): their chunked scan made delete detection depend on DB ordering — the review objection that sank it; ours keeps ordering out of the design. |
| **05**<br>`fsevents-journal-replay` | **Problem.** Every Mac boot began with a full-tree scan: ≈40 min after 5.8 h offline, while fseventsd had already recorded exactly what changed.<br><br>**Principle.** Replay the journal instead of rediscovering by walking; the OS is already the change log.<br><br>**Details.** Boot-time journal replay replaces the initial full scan; journal overflow heals with a subtree/full scan without killing the watch; pins the notify fork.<br><br>**Effect.** Boot after 5.8 h offline: ≈40 min scan → 6 s replay of 4.17M journal events (measured). | Mitigates [#5353](https://github.com/syncthing/syncthing/issues/5353) (skip startup rescan — ISSUES.md: "we built the thing this issue wants"). |
| **06**<br>`btrfs-scan-replay` | **Problem.** The Linux receiver needed the same boot answer as the Mac, but has no FSEvents: a post-reboot full walk of the tree on 7200rpm RAID1 costs 14–45 min of seeks.<br><br>**Principle.** A btrfs snapshot pair is a filesystem-level diff: compare the two snapshots and scan only what changed, instead of walking the tree.<br><br>**Details.** Snapshot-diff replay at boot; shutdown-paired scans so a baseline always exists; per-run completeness gating; 32-bit-safe btrfs magic compare (CI-found).<br><br>**Effect.** Post-reboot scan: 14–45 min → seconds when a baseline is paired (the "15 s boot"). | Mitigates [#5353](https://github.com/syncthing/syncthing/issues/5353) on the Linux side. |
| **07**<br>`btrfs-helper-ops` | **Problem.** Snapshot create/delete needs root; syncthing runs as a user, and patching that gap with blanket sudo would put root in the hot path of every boot.<br><br>**Principle.** Put exactly the privileged verbs behind a socket-activated helper with a tiny, auditable surface; root activates on demand and does nothing else.<br><br>**Details.** systemd socket units + helper scripts under `ops/`; amended by patch/44 so ignored nested subvolumes no longer disable scan replay.<br><br>**Effect.** Unprivileged boot/shutdown snapshot pairing on yarlung — the enabler for 06/13/19/44/45. No time number: the win is capability without a standing root process. | — |
| **08**<br>`watch-buffer-batch-throttle` | **Problem.** Build bursts overflowed the watch pipeline's 500-entry backend buffer; each overflow escalated to full-folder watch batches, and those fired full-tree scans — dogfooded 2026-10-17: hourly full scans (≈6–9 min each) triggered by our own builds.<br><br>**Principle.** Backpressure beats overflow: absorb bursts in a deep buffer, skip redundant batches while a scan is already running, and when the aggregator must degrade, degrade to the affected subtrees — never the whole tree.<br><br>**Details.** Backend buffer 500 → 65536 (131×); full-folder watch batches skipped during a full scan; aggregator overflow collapses to common prefixes.<br><br>**Effect.** The hourly build-burst scan cycle is gone; overflow now costs a subtree scan instead of a 2.38M-file walk. | Overlaps declined PR [#10774](https://github.com/syncthing/syncthing/pull/10774) — our deeper buffer changes the overflow regime it assumed. |
| **09**<br>`gui-event-loop` | **Problem.** The GUI's event stream ran on browser timers, which background tabs throttle to ≈1/min: a backgrounded GUI went blind exactly while bulk work was happening.<br><br>**Principle.** Timer throttling is environmental; a fetch-based event loop has no timers to throttle.<br><br>**Details.** Fetch-based GUI event loop; CSRF header on the poll.<br><br>**Effect.** The GUI stays live in background tabs. Not a throughput number — the class of stall is eliminated. | — |
| **10**<br>`need-tables` | **Problem.** Every need query (out-of-sync view, pull queue) derived its answer from the folder table on the spot — a scan-sized read for a question that changes one row at a time.<br><br>**Principle.** Maintain the answer incrementally as updates land; reads become table lookups.<br><br>**Details.** Incrementally maintained need-tracking tables; `folderDB.Close` waits for the async builder so test tempdirs close cleanly on Windows (CI-found).<br><br>**Effect.** Need queries read maintained state. Together with 03 and 17 this is the need-query story: the upstream reporter's median for the underlying iteration went from 40.5 s to 1.3 s on a large tree. | — |
| **11**<br>`gc-lock-scope` | **Problem.** GC held the folder `updateLock` for minutes at a time; everything behind it — including device connection bookkeeping — waited, and waits turned into lost connections (the #10372 class). On yarlung, each blocked commit additionally risks a 58 ms fsync convoy.<br><br>**Principle.** Hold the lock for one chunk of work; make writers queue in the database (busy_timeout), not on the application lock.<br><br>**Details.** GC releases updateLock between chunks and never re-acquires inside GC; busy_timeout added (with 15: raised 5 s → 30 s).<br><br>**Effect.** With 15, the measured outcome (patch/15 era): the ≈20 s flap loop with 172 lock errors in one session and a frozen index became zero lock errors since dev.92. | Fixes [#10529](https://github.com/syncthing/syncthing/issues/10529) (with 15); mitigates [#10372](https://github.com/syncthing/syncthing/issues/10372), contributes to [#10868](https://github.com/syncthing/syncthing/issues/10868). |
| **12**<br>`fsevents-rearm-after-scan` | **Problem.** Journal replay armed only at boot; after an overnight gap the watermark was stale, arming refused, and replay stayed off for the process lifetime. Every fseventsd drop flag (≈22/min on the busy tree) then escalated to a full rescan — measured 2026-10-13: 5,566 scan-state transitions in 2 h 47 min, zero replay engagements; the folder looped through ≈20-min scans endlessly.<br><br>**Principle.** A completed scan makes the DB complete as of the journal's current position — that is all arming requires; the stale-watermark refusal belongs to boot only.<br><br>**Details.** Replay arms after any completed full scan, not just at boot.<br><br>**Effect.** The scan-loop class is eliminated: after the next completed scan the watcher returns to event-driven mode instead of 20-min full scans forever. | — |
| **13**<br>`btrfs-canary-barrier` | **Problem.** A snapshot baseline paired against the wrong index state is worse than no baseline: the boot diff would replay changes the index already has (or miss ones it lacks), silently.<br><br>**Principle.** Pair by proof, not by timing: a canary file written before the baseline snapshot must be visible in the index afterwards — then the two provably belong together.<br><br>**Details.** Canary barrier pairs baseline with index; runtime baseline refresh; canaries pass the watch ignore filter; test helper collects GC-garbage dir handles before tempdir removal on Windows (CI-found).<br><br>**Effect.** Boot replay (06) can only run on a proven-consistent pair; a broken pairing degrades to a full walk, never to a wrong index. | — |
| **14**<br>`fsevents-poll-mode` | **Problem.** The live FSEvents stream was the unreliable part of the Mac watch: the notify stream leaked memory unboundedly ([#10894](https://github.com/syncthing/syncthing/issues/10894)) and stream state could silently desync from the journal.<br><br>**Principle.** Poll the journal on a cadence and filter our own writes server-side; a stateless consumer holds nothing and therefore cannot leak or desync.<br><br>**Details.** 5 s poll-mode replay replaces the live stream; IgnoreSelf (own writes filtered at the source) as a serve-startup opt-in.<br><br>**Effect.** The unbounded-watch-memory class is gone on the Mac; watch state cost is the poll loop, O(1) in tree size. | Mitigates [#10894](https://github.com/syncthing/syncthing/issues/10894) (the notify fix is carried via the pinned fork; poll mode removes our dependence on the stream). |
| **15**<br>`db-busy-resilience` | **Problem.** One SQLITE_BUSY was fatal to the index handler: it killed the device connection. On yarlung, where a commit can wait behind a 58 ms fsync convoy, contention windows are wide.<br><br>**Principle.** Lock contention is transient; retry with bounded backoff and give the database a real busy_timeout instead of treating busy as broken.<br><br>**Details.** Index updates retry on lock contention with bounded backoff; busy_timeout 5 s → 30 s.<br><br>**Effect.** Contention costs a wait, not a connection. With 11, the #10372 "lost device connection" class is marked likely-fixed; no recurrence on our workload. | Fixes [#10529](https://github.com/syncthing/syncthing/issues/10529) (with 11); mitigates [#10372](https://github.com/syncthing/syncthing/issues/10372). |
| **16**<br>`watch-flush-wait` | **Problem.** The baseline pairing asked the watch aggregator to flush and gave up instantly if it was busy — aborting a valid pairing, and with it the next boot's fast path (a 14–45 min walk instead of seconds).<br><br>**Principle.** Busy is not broken: a bounded wait converts a spurious failure into a slow success.<br><br>**Details.** The flush request waits up to 15 s for the aggregator.<br><br>**Effect.** Pairing survives aggregator-busy windows; the boot fast path stops being lost to a timing race. | — |
| **17**<br>`files-needed-index` | **Problem.** The local pull-queue query scanned every file in the folder to find the few it needs — the upstream reporter measured a 40.5 s median file iteration on a large tree. On yarlung's spindles the same cold iteration is a seek storm (6.7 ms per uncached page).<br><br>**Principle.** Let the database keep the answer: a partial index over exactly the rows the pull queue can ask about.<br><br>**Details.** `files_needed` partial index, adopted from the unmerged upstream fix with mutation-verified tests.<br><br>**Effect.** The reporter's iteration: 40.5 s median → 1.3 s (31×) with the index. Our pull-queue queries take the indexed path. | Fixes [#10902](https://github.com/syncthing/syncthing/issues/10902) (adopted the unmerged fix); overlaps [#10906](https://github.com/syncthing/syncthing/pull/10906) (may subsume — not verified equivalent). |
| **18**<br>`scan-observability` | **Problem.** Fast-path skips were silent: when scan replay bailed or a pairing marker was consumed without a replay being possible, nothing was logged — misbehavior had no evidence trail (found by dogfooding: the btrfs probe ran even when journal replay had already armed).<br><br>**Principle.** Every decision that skips work must leave a log line saying why; markers are consumed only when the work they gate can actually run.<br><br>**Details.** Full-scan outcomes and btrfs replay bail reasons logged; pairing marker consumed only when replay is actually attempted; btrfs probe skipped once replay is armed.<br><br>**Effect.** The 12/19/44-class investigations became minutes of log reading instead of days of guessing — every later "found by dogfooding" row stands on this. | — |
| **19**<br>`btrfs-repair-after-replay` | **Problem.** After a boot diff replay, re-arming the baseline pairing failed inline — observed on yarlung 2026-10-16: "watch not running" 15 s after boot, because the aggregator was still in its setup pass. With rescanIntervalS=86400 the next full-scan refresh was a day away, leaving every restart in between uncovered.<br><br>**Principle.** Boot-time work races other subsystems' startup; retry on a bounded timer instead of assuming the world is ready.<br><br>**Details.** Serve-loop retry timer re-arms the pairing after a boot replay; bounded tries, then a clean give-up with a log line.<br><br>**Effect.** The uncovered-restart window closes: pairing lands within minutes of boot instead of "maybe tomorrow". | — |
| **20**<br>`stale-request-repair` | **Problem.** A missed local change left the index claiming a file existed while disk said ENOENT — and the remote retried forever: one manifest retried 9,449 times over 17 h (dogfood 2026-10-18), ≈9 pointless request round-trips per minute, indefinitely.<br><br>**Principle.** An ENOENT against a positive index entry is a self-healing signal: feed the path back into the scanner instead of failing the request forever.<br><br>**Details.** The failing request feeds the path into the watch aggregator: debounced subtree scan, tombstone, requester converges.<br><br>**Effect.** Stale-index request storms terminate on their own; the 17-hour retry loop class becomes a one-subtree-scan repair. | — |
| **21**<br>`adaptive-scan-budget` | **Problem.** The scan chunk boundary forced a commit flush every 250 ms even with nothing queued — an idle machine paid 4 forced commit cycles per second — and a 197k-entry deletion sweep was observed at ≈100 marks/s at 0 % CPU with no code path explaining it (2026-10-19).<br><br>**Principle.** Adapt the quantum to the queue: grow it while boundaries find nothing, snap back the moment real work appears; instrument the sweep so cost mysteries have numbers.<br><br>**Details.** Chunk budget doubles at idle boundaries (250 ms → 5 s cap), snaps back on serviced work; the deletion sweep logs per-chunk entries/marks/wall/boundary/per-entry cost.<br><br>**Effect.** Idle-tree scans commit up to 20× less often; a busy machine keeps fine-grained sharing; the next sweep anomaly will have per-chunk cost data instead of a shrug. | — |
| **22**<br>`bulk-delete-collapse` | **Problem.** Deleting a large tree cost a database read + stat + remove + event per file — the firefox checkout case: ≈197k entries, ≈197k of each.<br><br>**Principle.** When the round's tombstones provably cover everything under a directory, one verified `RemoveAll` is exactly equivalent to the per-file walk — prove coverage first, then take the fast path.<br><br>**Details.** A verification walk aborts to per-file on any untracked file, local modification, conflict, or read error; ignored non-deletable entries keep the tree; never runs with a versioner. Index updates queue in bulk.<br><br>**Effect.** The ≈197k-entry tree removal becomes one syscall-side walk; the per-file machinery only runs when verification finds something it cannot prove. | — |
| **23**<br>`passive-checkpoints` | **Problem.** WAL checkpoints on the update path used RESTART/TRUNCATE semantics: they must wait for readers, the scan sweep's own iteration snapshot is a reader, and the retry escalation ground the serve loop to ≈100 marks/s at 0 % CPU — full stall, no work done (goroutine-profile attribution, 2026-10-19).<br><br>**Principle.** A checkpoint on the update path must never wait: PASSIVE checkpoints what it can and leaves the rest; the WAL drains once readers finish.<br><br>**Details.** Update-path checkpoints become PASSIVE; the WAL stays bounded by `journal_size_limit` and drains fully when the machine is quiet.<br><br>**Effect.** The 0 %-CPU stall class is gone; verified live ever since: the WAL checkpoints down to exactly 8,388,608 B whenever yarlung is idle. | Mitigates [#10529](https://github.com/syncthing/syncthing/issues/10529) (inferred: PASSIVE avoids the reader-blocked checkpoint contention); overlaps PR [#10556](https://github.com/syncthing/syncthing/pull/10556) (inferred: same technique, different path). |
| **24**<br>`ring-log-sink` | **Problem.** Every logging goroutine wrote to the log file directly: a slow disk or stalled consumer stalled all of them, and a `--no-restart` run that panicked lost exactly the log record that explained the panic.<br><br>**Principle.** Logging is a producer/consumer problem: producers write to a fixed memory ring and never touch the file; one drainer goroutine does all the I/O.<br><br>**Details.** 32k-line ring (`STLOGRINGLINES`); gap marker with drop count on wrap; panic dumps the ring to `panic-<timestamp>-ring.log`; exit path flushes with a 2 s deadline.<br><br>**Effect.** Logging can no longer stall the system it is observing; the last seconds before a crash are preserved even with no monitor process. | — |
| **25**<br>`monitor-reexec-path` | **Problem.** Upgrades replaced the running binary's target, so a restart re-executed the *old* resolved path — an in-place upgrade over a stable symlink was impossible, and every deploy was a manual dance on two machines.<br><br>**Principle.** Re-exec the invocation path, not the resolved binary; then a stable `current` symlink plus one API call upgrades the binary in place.<br><br>**Details.** Monitor re-execs the invocation path. Live wrinkle (dev.155): staging the new binary into the synced folder in the same second as the restart loses the FSEvent, so the new binary never reaches the index or the peer — remedy built into the deploy scripts (`POST /rest/db/scan?folder=home&sub=syncthing-custom`). | **26**<br>`log-traps` | **Problem.** Forensics needed the verbose log around an interesting event, but running verbose permanently drowns the signal — the interesting moment was always in the part nobody had enabled.<br><br>**Principle.** Arm a matcher at runtime: when a matching line enters the ring, dump the recent past, elevate the named packages for a window, dump again at close, restore levels.<br><br>**Details.** `POST /rest/system/logtraps`; substring-first matcher with a RE2 escape hatch; the logging package's own lines are exempt so traps cannot self-trigger; zero overhead when nothing is armed.<br><br>**Effect.** Post-hoc verbosity: the past is captured from the ring (24) at the moment it matters, without paying for it before or after. | — |
| **27**<br>`concurrent-deletions` | **Problem.** Deletions waited for the pull pipeline to drain: a delete wave arriving during a large pull round (old browser checkout deleted while the new one pulls) queued behind the whole round — tens of thousands of pending deletes on the live system.<br><br>**Principle.** Only deletions whose blocks feed in-flight pulls can conflict with them; everything else can proceed immediately.<br><br>**Details.** The need walk collects the block hashes of every queued pull; only deleted files whose blocks intersect that set defer to the post-drain pass; all other deletions run concurrently with the pulls.<br><br>**Effect.** Delete waves apply during pull rounds instead of after them; the queue length stops being the deletion latency. | — |
| **28**<br>`sqlite-page-cache` | **Problem.** SQLite's 8 MiB default page cache thrashed on a multi-GiB folder DB on slow storage — measured on yarlung: the post-restart need scan ran at ≈400 rows/min at 1 % CPU, all I/O wait on the 8.8 GiB DB, every row costing three random join probes plus a point lookup — each uncached page a 6.7 ms seek.<br><br>**Principle.** Give the cache an explicit budget sized to the working set; small databases grow on demand and pay nothing.<br><br>**Details.** DSN-level per-connection budget (256 MiB total across the pool by default, floor 8 MiB, `STDBPAGECACHEMIB`) so late-opened pool connections get it too.<br><br>**Effect.** The need scan stopped being seek-bound; the cache budget is why yarlung's C-side SQLite sits at ≈423 MB RSS (FORK.md's machine comparison) — a deliberate trade: RAM for seeks. | — |
| **29**<br>`deletes-before-queue` | **Problem.** patch/27's deferral still waited: the deletion pass started only after `processNeeded` returned, and that includes the queue-pop loop that feeds every queued pull to the copier pipeline, throttled by fetch rate — observed live on yarlung: the puller parked in the queue loop with 88k deletes pending.<br><br>**Principle.** The deferral split belongs in the walk itself: deletions start immediately, the queue feeds concurrently.<br><br>**Details.** The walk performs the split; the deletion goroutine starts at once; rename sources defer via block-list-hash match (covers the zero-block case per-block overlap misses).<br><br>**Effect.** The 88k-delete parking case is gone; deletion latency no longer includes the whole pull round. | — |
| **30**<br>`collapse-abort-logging` | **Problem.** patch/22's verification aborted silently: the first live firefox-tree delete fell back to ≈88k per-file deletes with `verifyFailed=1` and no clue why.<br><br>**Principle.** A verifier that can abandon 88k deletes must say what it found and why.<br><br>**Details.** `verifyDeleteTreeCovered` returns the first offending path plus a reason; the caller logs both. | **31**<br>`collapse-covers-deferred` | **Problem.** Found by 30 on the first live firefox delete: one byte-identical git sample file (`.git/hooks/applypatch-msg.sample`), deferred by 29 as a rename source for the incoming checkout, read as "not in this round's deletion set" — and all ≈88k deletes of that tree abandoned to the per-file path.<br><br>**Principle.** Deferred entries are deleted later the same round; the collapse merely takes them slightly early, so they count as covered.<br><br>**Details.** The rename consumer falls back to fetching if its source is already gone; the deferred pass tolerates the file having vanished. | **32**<br>`collapse-covers-residue-dirs` | **Problem.** Found by 30 on the second live pass: an interrupted deletion pass (restart mid-flight) leaves directories on disk whose tombstones were already consumed — the index says deleted, the rmdir never happened — and that residue aborted the collapse of the whole containing tree.<br><br>**Principle.** A directory already deleted in the index is covered: the walk still descends and verifies every entry inside it individually. | **33**<br>`collapse-skips-pull-trees` | **Problem.** Composition corner of 22+27+29 found by adversarial review: a pull queued or in flight *under* a collapse root (multi-device inconsistency — tree deleted on one device, an entry alive on another; the live uikit case) would have its freshly written or renamed file destroyed by the RemoveAll.<br><br>**Principle.** Multi-device inconsistency is legal input; the collapse must skip any root the job queue touches.<br><br>**Details.** `ContainsPathUnder` over queued + in-progress names; membership only shrinks after the need walk, so one check per root is sound. | **34**<br>`wal-autocheckpoint` | **Problem.** SQLite's 1000-page (≈4 MiB) default autocheckpoint fired after every ≈4 MiB of commits — during pulls, several times a minute — each flush writing up to 4 MiB of *random* pages into the 9.3 GiB folder DB, CoW-amplified by btrfs. | **35**<br>`syncfs-batch-durability` | **Problem.** Root cause of the remaining write amplification after 34: ≈2 fsyncs per pulled file (temp file + parent dir), and on btrfs each fsync forces a log-tree commit of ≈0.8 MB. | **36**<br>`db-nocow-auto` | **Problem.** On CoW filesystems, operators had to remember `chattr +C` on the index directory by hand; forget it and every checkpoint rewrites random pages as fresh extents (the CoW amplification behind the ≈0.8 GiB/min bursts measured while `syncing`).<br><br>**Principle.** Detect the filesystem at open (statfs → btrfs/bcachefs) and apply NOCOW before the database/WAL/shm are created, so they inherit it from birth.<br><br>**Details.** `FS_IOC_SETFLAGS` needs `IoctlSetPointerInt` (value-passing returns EFAULT — found live); btrfs silently ignores NOCOW on files with extents, so the code verifies the flag after setting and only claims success when it sticks; NOCOW implies NODATASUM for new writes (same tradeoff as manual `chattr +C`); `STDBNOCOW=0` opts out; failures log, never block open.<br><br>**Effect.** No operator step; new database files are NOCOW from creation. | **37**<br>`mtime-write-batching` | **Problem.** The mtimeFS virtual-time store is advisory, yet every directory mtime update was a synchronous database transaction — observed on yarlung 2026-10-20: the post-restart need walk blocked in `DeleteMtime` behind index batch commits, progressing at ≈6 items/min on the 7200rpm RAID1 (each micro-transaction queued behind 58 ms-class durability points).<br><br>**Principle.** Advisory state gets advisory durability: batch it in memory, flush on size or latency, read-your-writes.<br><br>**Details.** `PutMtime`/`DeleteMtime` enqueue into a per-folder pending map (last op per name wins), flushed by one transaction at 512 ops or 2 s; `GetMtime` reads through the pending map; `Close` flushes. | **38**<br>`nocow-auto-migrate` | **Problem.** patch/36 could only flag *new* files: btrfs silently ignores NOCOW on files with extents, so the pre-existing 9.3 GiB folder DB stayed CoW and every 1 GiB-WAL checkpoint rewrote random pages as fresh extents — the ≈0.8 GiB/min device-write bursts measured while `syncing`.<br><br>**Principle.** Migration is a pure function of observable state (CoW filesystem ∧ flag unset ∧ free ≥ 1.1× set size): decide deterministically, copy byte-identically, rename atomically; every crash-interrupted mix is consistent because the copies are identical bytes.<br><br>**Details.** DB + WAL migrate as a set (an empty-WAL gate would defer forever — the pool never checkpoint-removes it at close); copy to sibling temp, fsync, rename all + dir fsync; self-terminating; `STDBNOCOW=0` opts out; off Linux the gate is a stub false (APFS has no NOCOW concept; CoW is free on flash).<br><br>**Effect.** yarlung's 9.49 GiB folder DB migrated in 22 min one-time on busy spindles (main.db: 154 ms); the 1 GiB-checkpoint-into-CoW bursts are gone — the nine live NOCOW checkpoints captured afterwards showed 2.04× excess writes = pure RAID1 mirroring, zero CoW amplification. | — |
| **39**<br>`larger-dbupdater-batches` | **Problem.** The pull path committed DB updates in batches of 1000 files / 5000 blocks / 2 s — constants copied from the wire Index batch. | **40**<br>`checkpoint-nocow-coupling` | **Problem.** The right WAL autocheckpoint threshold depends on the storage regime: under CoW a checkpoint is a random-page rewrite storm (100× cost class), under NOCOW it is in-place and cheap (nine live checkpoints: 2.04× excess = pure RAID1 mirroring). | **41**<br>`db-auto-defrag` | **Problem.** A NOCOW database copied under writeback congestion landed severely extent-fragmented: 9.4 GiB in 210,094 extents (≈45 KiB average, vs 2 extents for the same write on the idle filesystem). | **43**<br>`cyclical-maintenance-scheduling` | **Problem.** Nightly maintenance (41's defrag) must run when the machine is idle, but a fixed clock time is wrong on a machine with irregular use — and the first live fire proved it: the scheduler fired at 21:15 because "now > pick" with no marker (the catch-up bug).<br><br>**Principle.** Learn the usage rhythm from the system itself: the log rate tracks sync churn, so the slog sink already carries the activity signal — histogram it, pick the learned idle window, jitter deterministically.<br><br>**Details.** `internal/activityhist`: minute-of-day + hour-of-week histograms with weekly halving decay, persisted as `activityhist.json`; per-job duration EMA feeds a 2× admission gate; minute-tick scheduler writes `.defrag-pending` flags and self-restarts via the API restart path; window admission limited to [pick, pick + min(runLen, 3h)) after the 21:15 regression; `STMAINTENANCETIME=HH:MM` pins, `STDBDEFRAG=1` forces.<br><br>**Effect.** Maintenance lands in the measured idle window instead of a guessed clock time; boot-time cost is zero unless maintenance decided it. | — |
| **44**<br>`db-nested-subvolume` | **Problem.** Root-caused the mystery of NOCOW "not sticking": the database re-fragmented 3 → 104,235 extents in 2 h despite the C flag, because btrfs honors NOCOW only on unshared extents — and the fork's own boot-time baseline snapshots re-share them, with the database inside /home. If content changes while an mtime bump is held, the fresh scan carries the fresh mtime and the stale held entry is dropped — committing the old one after the new one would regress the index. Overnight 2026-10-23 to 24: receiver WAL +3.7 MB in 12 h (no checkpoint can have masked it — the >=128 MiB threshold was never reached) vs ~0.8 GB expected at the prior ~1.1 MB/min rate; end-to-end liveness probe 16 s; zero errors, zero panics both ends. Receive-only folders excluded: a local delta there is an aberration queued for revert, and holding it delays repair bookkeeping.
