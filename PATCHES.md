# Maintained patches on top of upstream Syncthing

This file is the inventory of the patches this fork carries. It lives on the
fork's `main` branch, whose history is upstream plus one commit per patch,
then the fork's documentation. See `FORK.md` for how the
fork is maintained and rebased.

Upstream tracking issue: https://github.com/syncthing/syncthing/issues/10921
(presents the six headline changes with measurements; PRs offered one per
patch if upstream wants them).

Patches are listed in history order. Each patch is one commit on `main`
whose subject starts `patch/<slug>:`; the slug is the patch's stable name.
A fix to a patch is folded into that patch's commit, never added as a
patch of its own, so every commit is one complete change that upstream can
take on its own. Its message keeps the folded revisions as sections, and
its design record, where it has one, is `patches/<slug>.md`. Each table
row states the patch as it is now, with its latest measured effect; how it
got there (one entry per folded revision, with the problem that caused it)
is in the History section at the end. (Until
2026-11-22 patches were numbered and fixes were separate patches; the
table at the end maps the old numbers to slugs.)

## How to read this

Each row below is one observed problem and one shipped answer. Problem and
Effect stand independently of the mechanism; alternatives that solve the same
problem are legitimate discussion — the numbers are the argument, not the
code. Measured numbers come from the machine constants below; derived
arithmetic is marked with ≈. The two production machines:

(measured 2026-10-24)

Method: cache-bypassed reads on the live folder databases (Mac 8.1 GiB, yarlung 9.7 GiB), temp-file writes in the database directory, 2000-sample random reads, 200-sample fsync loop. All patch impact calculations in this document derive from these constants.

| | **Mac** — MacBookPro18,2, M1 Max 10-core, 64 GB, NVMe/APFS | **yarlung** — Ivy Bridge 4C/8T (2012), 15 GB, 2×7200rpm RAID1, btrfs |
|---|---|---|
| Sequential read | 9.9 GB/s (the 8.1 GiB DB is fully RAM-resident) | 150 MB/s |
| Sequential write + fsync | 2.2 GB/s | 95 MB/s |
| Random 4K read, p50 | 2 µs (warm cache) | 6.7 ms (cache dropped — a real head seek) |
| fsync of a 4K write, p50 | 36 µs | 58 ms (btrfs log-tree commit) |

The asymmetry in one line: a random database touch costs **~3000×** more on yarlung, a durability point **~1600×** more. Every patch below exists because of one of those two ratios.

| `skip-mtime-on-exists` | **Problem.** Every existence check during a scan paid a virtual-mtime database lookup whose result was never used — 2.38M lookups per full scan. A lookup costs one page read: 2 µs when the page is in RAM, 6.7 ms when it must be sought from disk (machine constants above). Per full scan that is ≈5 s warm, up to ≈4.4 h cold.<br><br>**Principle.** Don't pay for information you don't use: an existence check needs no mtime.<br><br>**Details.** `LstatExists` bypasses the mtimefs lookup through the whole wrapper stack; each wrapper ordering (case-fs, log-fs, walkfs) has its own test.<br><br>**Effect.** Mac (documented in [#10909](https://github.com/syncthing/syncthing/issues/10909)): on stock v2.1.5 the deleted-and-ignored pass alone sat in `GetMtime` for 1 h 44 min without finishing, pulls starved behind it; with the fix the full scan completes in 6–9 min. yarlung: a cold full-tree existence pass drops ≈4.4 h of seeks to zero for this cost class; full scans there are rare anyway since patch/btrfs-scan-replay. | [#10909](https://github.com/syncthing/syncthing/issues/10909) — filed by us with these measurements, closed as not-planned 2026-10-15. |
| `gc-chunked-commit` | **Problem.** Orphan-block GC ran as one transaction across a 45.5M-row blocks table; on a multi-GB index it aborted after 5 minutes, leaving a huge WAL and only a few chunks done — the next run started from zero. Each retry paid the same 5 minutes.<br><br>**Principle.** Long work belongs in bounded chunks that commit and release; interruption then costs at most one chunk.<br><br>**Details.** GC commits per hash-range chunk; blocklist hashes are retired when the block index updates instead of in a full GC scan; the needs-full-scan flag survives an interrupted GC.<br><br>**Effect.** GC completes incrementally and resumes after interruption instead of restarting. No wall-time comparison recorded — the measured fact is structural: 5-minute aborts with zero progress are no longer possible. | [#10868](https://github.com/syncthing/syncthing/issues/10868) — frequent GC with many small files; fixed for ourselves. |
| `need-list-perf` | **Problem.** Need queries (what does the peer lack?) re-ordered and re-computed results on every call — SQL name-ordering plus uncached remote need lists over a 2.38M-row table. On a cold yarlung, each uncached index page is a 6.7 ms seek.<br><br>**Principle.** Cache what is expensive to recompute; order only when a consumer needs the order.<br><br>**Details.** No SQL name ordering in need queries; cached remote need list; cached per-device need count; iterator cost accounting so regressions are visible.<br><br>**Effect.** Need views answer from cache instead of rescanning the table per call. The remaining cold iteration cost is covered by patch/files-needed-index's partial index (upstream reporter's numbers on a large tree: 40.5 s median → 1.3 s). | — |
| `chunked-scan` | **Problem.** A full scan monopolized the folder's Serve loop: pulls and watch events queued behind the walk (the #10909-era scan held the loop for 1 h 44 min with `needFiles=2` waiting; a yarlung full walk takes 14 min to 2 h). Two failure shapes followed inside the scan itself. A watch batch dequeued between chunks was scanned nested inside the running scan: on the Mac a full-folder batch nested inside a subtree scan held the folder in `scanning` for 2 h 38 min. And a pull that found disk and index disagreeing asked for a rescan that only ran after the initial scan: on yarlung, 2026-11-25 18:47 to 11-26 16:30, a 21h43m initial scan ran alongside 1,823 failed pull passes and 6,471,843 "Failed to delete file" lines for 1,988 files already gone from disk.<br><br>**Principle.** A scan is resumable and yields: it runs in timer-budgeted chunks, services queued work at each boundary, never runs a scan inside a scan, and runs any rescan the pull depends on before the next pull pass.<br><br>**Details.** Resumable walk; the chunk budget starts at 250 ms, doubles at idle boundaries up to 5 s and snaps back when a boundary services work. Pulls and watch events are serviced between chunks and during the deletion sweep, which logs per-chunk entries, marks and cost. A dequeued watch batch is integrated when the walk has not reached its paths yet (walk-order compare against the resume marker); otherwise it is deferred into one bounded pending set (`BoundedPathSet`, 4096 paths) that the Serve loop scans as one scan when the running scan returns. The replay watermark never passes a deferred batch. Pull rescans: `pullRescanCollector` queues names before `pull` returns, and `servicePullRescan` rescans all of them at the next walk or sweep boundary (or from the Serve loop when no scan runs), never nesting more than one level; this replaces `pullScannerRoutine`. Counters: `syncthing_model_folder_watch_batches_{integrated,deferred}_total`, `..._watch_pending_scans_total`, `..._pull_rescan_names_total`.<br><br>**Effect.** End-to-end change latency 10–23 s under storm load, deletes included; idle-tree scans commit up to 20× less often. Fail-before/pass-after: `TestServiceQueuedWatchNeverNests`, `TestScanChunkedServicesWatchEvents`, `TestPullRescanDuringInitialScan` ("gone is still live in the local index after a pull and a scan that ran past it"), `TestPullRescanServicesWholeQueue`. Production (dev.197): the Mac deferred 10 batches into 8 pending scans in 1.5 h; yarlung deferred 5 and rescanned 2 pull-flagged names in 1 h. The pull-rescan livelock has not recurred: yarlung's logs from 11-27 11:16 to 11-28 00:12 hold 17 "file modified but not rescanned" lines, all between 16:20:38 and 16:20:42 (7 files under `ssb/statbus-marks/test/expected/`, during a full scan), and none after (the 21h43m episode logged 6.47M). | Watching [#10264](https://github.com/syncthing/syncthing/issues/10264) (SQLite at scale — same wall, different attack); [#8418](https://github.com/syncthing/syncthing/issues/8418) adjacent. Compare [#10516](https://github.com/syncthing/syncthing/pull/10516): their chunked scan made delete detection depend on DB ordering — the review objection that sank it; ours keeps ordering out of the design. |
| `fsevents-journal-replay` | **Problem.** Every Mac boot began with a full-tree scan (≈40 min after 5.8 h offline) while fseventsd had already recorded what changed. After an overnight gap the watermark was too old to arm replay, which then stayed off for the process lifetime: every fseventsd drop flag (≈22/min) became a full rescan, 5,566 scan-state transitions in 2 h 47 min with zero replay engagements (2026-10-13).<br><br>**Principle.** Replay the journal instead of rediscovering by walking. A completed scan makes the index complete as of the journal's current position, which is all arming requires; the stale-watermark refusal applies at boot only.<br><br>**Details.** Boot-time journal replay replaces the initial full scan; journal overflow heals with a subtree or full scan without killing the watch; replay re-arms after any completed full scan. Pins the notify fork.<br><br>**Effect.** Boot after 5.8 h offline: ≈40 min scan → 6 s replay of 4.17M journal events. The 20-min scan loop is gone: after the next completed scan the watcher returns to event-driven mode. | Mitigates [#5353](https://github.com/syncthing/syncthing/issues/5353) (skip startup rescan — ISSUES.md: "we built the thing this issue wants"). |
| `btrfs-scan-replay` | **Problem.** The Linux receiver has no FSEvents journal, so every boot walked the whole tree: 14–45 min on a good day on the 7200rpm RAID1, 1h21m44s on 11-25 and 2h2m28s on 11-27. A btrfs snapshot diff can replace the walk, but only against a baseline provably paired with the index, and every way the pairing failed meant a full walk: guessed quiet periods, a busy aggregator, a watch setup of 34–40 min (476,322 inotify watches), shutdown deadlines longer than the supervisors and systemd allowed, a blanket 5 min helper timeout on the boot diff (three diffs past it fell back to full scans of 66 min, 4 h 20 min and over 13 h), a marker deleted when the boot read it, and a runtime pairing doing catch-up scans under a 2 min deadline.<br><br>**Principle.** Pair a snapshot with the index by proof, keep a recent pairing at all times, and replay the diff at boot. Every wait ends on a condition or on a measured cost, never on a guessed constant.<br><br>**Details.** *Pairing:* drain and flush the watch, read the local sequence, snapshot, canary barrier (a temp-prefixed file whose own inotify event proves FIFO delivery of everything before it, re-flushed every 250 ms), setbaseline, then a 32-byte marker (paired time, local sequence before the snapshot and after the barrier, local index ID). *When:* at shutdown, inside the folder's one `svcutil.ShutdownBudget` (120 s; `StopTimeout` 160 s, which the systemd drop-in sets as `TimeoutStopSec`); after a boot replay once the watch session is ready (`watchReady`); after a completed full scan; every 30 min while the index is provably complete (`fullScanOK`) and the watch is ready. A runtime pairing that finds deferred watch batches stands down and runs once the Serve loop has scanned them; it has no deadline, and its flush-drain and barrier end when the watch dies or a full-folder batch arrives. *Boot:* diff baseline against now; give up only at median(last 5 full scans) + median(last 5 diff cancel lags), with no limit while no full scan has been measured; rescan the diff's paths plus every local name written since the pairing's snapshot (`LocalNamesSinceSequence`), capped at 200,000 paths. The marker stays until the next pairing replaces it and is dropped when the index ID differs or the local sequence is below the recorded one. *Hygiene:* a boot sweep removes stale staging snapshots; snapshot cleanup gets its own bounded context; each pairing step logs `took=`; shutdown work still running 2 s past its budget logs the lib/model goroutine stacks, armed at cancellation.<br><br>**Effect.** yarlung boots after a paired shutdown: 210 ms (dev.196, 2026-11-27 19:34:47, 11 changed paths) and 201 ms (dev.197, 21:15:04, 4 changed paths) instead of a 2h2m28s walk; shutdown pairings 1–2 s; runtime pairings every 30 min. Fail-before/pass-after on Linux: `TestBtrfsRearmWaitsForWatchReady`, `TestBtrfsPeriodicPairing`, `TestFolderPathWaitsForShutdownWork`, `TestShutdownPairingHonoursBudget`, `TestWatchBarrierReflushesForLateCanary`, `TestBtrfsBootDiffWaitsWithoutScanMeasurement`, `TestBtrfsBootDiffGivesUpAtFullScanCost`, `TestBtrfsScanDiffBaselineNotCappedByHelperTimeout`, `TestShutdownOverrunLogsStacks`, `TestServeCancelOverrunLogsStacks`, `TestSystemdStopTimeoutCoversShutdown`, `TestBtrfsMarkerSurvivesBootUntilNextPairing`, `TestBtrfsReplayRescansIndexWritesSincePairing`, `TestRuntimePairingWaitsForDeferredBatches`, `TestPairingBarrierEndsOnWatchDeath`, `TestPairingDefersRootWatchBatch`. The 2026-11-26 22:00:41 stop overrun was traced by goroutine profiles to the database GC holding `updateLock` (fixed in `single-writer-invariant`). Not yet seen in production: a runtime pairing waiting out a backlog. | Mitigates [#5353](https://github.com/syncthing/syncthing/issues/5353) on the Linux side. |

| `watch-buffer-batch-throttle` | **Problem.** Bursts overflowed the watch pipeline, and every overflow became a full-folder scan. First a 500-entry backend buffer (hourly 6–9 min full scans triggered by our own builds, 2026-10-17); then the 65,536-entry buffer while the consumer was blocked (a boot journal replay pushed 69,773 events into it 2 s after a restart, the overflow's full scan took 27 min, and a poll replay overflowed it again 11 min later). Past the limit, events go into a 256-path `BoundedPathSet` that widens to ancestors, emitted as directory scans; canaries, fatal flags and out-of-root events stay ordered behind it. Aggregator window overflow collapses to common prefixes; a full-folder batch is skipped while a full scan runs; a drop flag with a subtree path rescans that subtree. notify `13a2142` defers boot-replay drop holes to one heal. Uncommitted means unannounced, so the receiver does zero work while an update is held, and a piggybacked flush arrives inside a batch the receiver was committing anyway. If content changes while an mtime bump is held, the fresh scan carries the fresh mtime and the stale held entry is dropped — committing the old one after the new one would regress the index. Overnight 2026-10-23 to 24: receiver WAL +3.7 MB in 12 h (no checkpoint can have masked it — the >=128 MiB threshold was never reached) vs ~0.8 GB expected at the prior ~1.1 MB/min rate; end-to-end liveness probe 16 s; zero errors, zero panics both ends. Receive-only folders excluded: a local delta there is an aberration queued for revert, and holding it delays repair bookkeeping. STMETABATCHWINDOWS=600 would give the quiet-period floor a 10-min batch; default stays at the derived 60 s | `mtime-only-metabatch` |

## History

How each patch got to its current state, oldest first. Every entry is one problem found in production or review and the revision folded into the patch; the row above states the result. Entries keep their original wording and dates, so numbers here describe the system at that time.

### `chunked-scan`

- **Revision (was `adaptive-scan-budget`).** **Problem.** The scan chunk boundary forced a commit flush every 250 ms even with nothing queued — an idle machine paid 4 forced commit cycles per second — and a 197k-entry deletion sweep was observed at ≈100 marks/s at 0 % CPU with no code path explaining it (2026-10-19). **Principle.** Adapt the quantum to the queue: grow it while boundaries find nothing, snap back the moment real work appears; instrument the sweep so cost mysteries have numbers. **Details.** Chunk budget doubles at idle boundaries (250 ms → 5 s cap), snaps back on serviced work; the deletion sweep logs per-chunk entries/marks/wall/boundary/per-entry cost. **Effect.** Idle-tree scans commit up to 20× less often; a busy machine keeps fine-grained sharing; the next sweep anomaly will have per-chunk cost data instead of a shrug.
- **Revision (no nested scans, 2026-11-24).** **Problem.** A watch batch dequeued between scan chunks was scanned right there, nested inside the running scan, walk and deletion sweep included: on the Mac a full-folder batch nested inside a subtree scan held the folder in `scanning` for 2 h 38 min, and a 41-path batch nested inside another subtree scan took 13 min 16 s. **Principle.** A scan never runs inside a scan: dequeue between chunks to keep the watch flowing, but either fold the batch into the running walk or defer it to one merged follow-up, with pulls and other work serviced in between. **Details.** A batch whose paths the running single-subtree or full walk has not reached yet (walk-order compare against the resume marker) is integrated: the walk and its sweep cover it. Anything else goes to a bounded pending set (`BoundedPathSet`, 4096 paths), which the Serve loop scans as one scan when the running scan returns; a new watch batch arriving meanwhile is merged into it. The replay watermark never passes a deferred batch: integrated and serve-scanned watermarks wait in the pending set until its scan succeeds. The btrfs pairing drains the pending set first and holds mid-scan dequeueing (its barrier must see its own canary); the shutdown drain includes the pending set. New counters `syncthing_model_folder_watch_batches_{integrated,deferred}_total` and `..._watch_pending_scans_total`; root-batch `where` labels are now `serve`/`between-chunks-skipped`/`between-chunks-deferred`/`pending`; "Slow scan finished" carries `pending` instead of `nested`. **Effect.** Fail-before/pass-after: `TestServiceQueuedWatchNeverNests` and `TestScanChunkedServicesWatchEvents` fail when the batch is scanned nested; `TestWatchBatchIntegratesAheadOfWalkFrontier` pins integration and watermark ordering. Production effect pending the dev.188 restart.
- **Revision (pull rescans at chunk boundaries).** **Problem.** When the puller finds disk and index disagreeing about an item it is about to change, it backs off with "file modified but not rescanned" and asks for a rescan. Upstream's rescan went through `Scan`, which waits for the initial scan to finish. With pulls running between chunks that is a livelock for the length of a long initial scan: on yarlung, 2026-11-25 18:47 to 11-26 16:30, a 21h43m initial scan ran alongside 1,823 failed pull passes, which logged 6,471,843 "Failed to delete file" lines for 1,988 files already gone from disk. Each pass failed about 3,550 deletes; the longest-repeating file failed 3,317 times between 21:17 and 16:02. The failed-pull stretches add up to at least 28,612 s (7h57m) of the scan, against 1h21m44s for the previous full scan (11-25). The folder WAL also exceeded its 512 MiB backstop from 08:19 (it reached 1.99 GB) until 16:29:39. **Principle.** A rescan the pull depends on must run before the next pull pass, not after the scan. Neither existing route qualifies: folding the names into the running walk records a deletion only in the sweep after the walk, and the pending set only runs once the scan returns. **Details.** The pull reports names through `pullRescanCollector`, which queues them before `pull` returns (`folder_pull_rescan.go`). `servicePullRescan` rescans every queued name at the next walk or sweep chunk boundary, or from the Serve loop when no scan runs, and puts them back if the scan fails. There is no per-boundary cap: the rescan is chunked itself and services pulls at its own boundaries, and the pull cannot progress on capped-off names until they are rescanned. It never nests more than one level, holds watch dequeueing so that no watermark is persisted out of order, and hands a root-path request to the scan timer. This replaces `pullScannerRoutine` in the send-receive, receive-only revert and receive-encrypted revert paths. New counter `syncthing_model_folder_pull_rescan_names_total`. **Effect.** Fail-before/pass-after: `TestPullRescanDuringInitialScan` (a file in the index, missing on disk and deleted by the peer, with the initial scan reopened) fails without the fix on both counts: "gone is still live in the local index after a pull and a scan that ran past it" and "the pull after the rescan still fails gone". It passes with the fix. `TestPullRescanServicesWholeQueue` fails with the first version's 4,096-name cap ("904 of 5000 queued names left for a later boundary after one rescan") and passes without it. No production measurement yet.

### `fsevents-journal-replay`

- **Revision (was `fsevents-rearm-after-scan`).** **Problem.** Journal replay armed only at boot; after an overnight gap the watermark was stale, arming refused, and replay stayed off for the process lifetime. Every fseventsd drop flag (≈22/min on the busy tree) then escalated to a full rescan — measured 2026-10-13: 5,566 scan-state transitions in 2 h 47 min, zero replay engagements; the folder looped through ≈20-min scans endlessly. **Principle.** A completed scan makes the DB complete as of the journal's current position — that is all arming requires; the stale-watermark refusal belongs to boot only. **Details.** Replay arms after any completed full scan, not just at boot. **Effect.** The scan-loop class is eliminated: after the next completed scan the watcher returns to event-driven mode instead of 20-min full scans forever.

### `btrfs-scan-replay`

- **Revision (was `btrfs-canary-barrier`).** **Problem.** A snapshot baseline paired against the wrong index state is worse than no baseline: the boot diff would replay changes the index already has (or miss ones it lacks), silently. **Principle.** Pair by proof, not by timing: a canary file written before the baseline snapshot must be visible in the index afterwards — then the two provably belong together. **Details.** Canary barrier pairs baseline with index; runtime baseline refresh; canaries pass the watch ignore filter; test helper collects GC-garbage dir handles before tempdir removal on Windows (CI-found). **Effect.** Boot replay can only run on a proven-consistent pair; a broken pairing degrades to a full walk, never to a wrong index.
- **Revision (was `watch-flush-wait`).** **Problem.** The baseline pairing asked the watch aggregator to flush and gave up instantly if it was busy — aborting a valid pairing, and with it the next boot's fast path (a 14–45 min walk instead of seconds). **Principle.** Busy is not broken: a bounded wait converts a spurious failure into a slow success. **Details.** The flush request waits up to 15 s for the aggregator. **Effect.** Pairing survives aggregator-busy windows; the boot fast path stops being lost to a timing race.
- **Revision (was `btrfs-repair-after-replay`).** **Problem.** After a boot diff replay, re-arming the baseline pairing failed inline — observed on yarlung 2026-10-16: "watch not running" 15 s after boot, because the aggregator was still in its setup pass. With rescanIntervalS=86400 the next full-scan refresh was a day away, leaving every restart in between uncovered. **Principle.** Boot-time work races other subsystems' startup; retry on a bounded timer instead of assuming the world is ready. **Details.** Serve-loop retry timer re-arms the pairing after a boot replay; bounded tries, then a clean give-up with a log line. **Effect.** The uncovered-restart window closes: pairing lands within minutes of boot instead of "maybe tomorrow".
- **Revision (snapshot hygiene).** **Problem.** The pairing ritual leaked: 12 stale shutdown/boot snapshots accumulated in 8 days in the helper's staging dir, one pinning a 9.6 GiB old database image, because deferred removals discarded their errors and process-exit races defeated them. **Principle.** Garbage is collectable from a pure name pattern at boot: anything `<trigger>-<folder>-<unixnano>` that isn't `baseline` is garbage by construction; failures at the source must be loud, not discarded. **Details.** Boot-time staging sweep using existing helper primitives (self-terminating, `STBTRFSSWEEP=0`); the two deferred removal sites now log WRN on failure. That WRN immediately caught a false failure ("rmsnap status 1" on every successful pairing: the rename to `baseline` had consumed the name), so the pairing defer stands down after setbaseline, and `btrfs-helper-ops` makes rmsnap idempotent. **Effect.** First boot swept 13 stale snapshots incl. one leaked 31 s earlier; staging holds only `baseline` ever since; the false-failure class is tested on both paths.
- **Revision (pairing reliability, 2026-11-25).** **Problem.** yarlung had no paired baseline after three failures in one day, so the next restart would do a full scan. (1) The shutdown pairing had its own 90 s deadline, but the supervisors on the folder path abandon a stopping service after suture's 10 s `ServiceTimeout` (silently, at debug); the app then closed the database under the running pairing ("Database failed to stop within 10s", 3 restarts on 11-24). (2) The post-replay re-arm retried on a timer: 20 tries × (30 s + 15 s flush timeout) ran out at 02:32, while notify was still adding 476,322 inotify watches synchronously before the aggregator (and its flush channel) existed. (3) A failed shutdown pairing meant a full scan: no pairing ran between boots. (4) The barrier flushed once; a canary event that reached the aggregator after that flush waited out the 10 s aggregation delay. **Principle.** Pair on readiness, not on a timer; keep the baseline fresh while running, so the shutdown pairing is a bonus; give shutdown one budget that every waiter above it honours. **Details.** `watchReady` per watch session, closed after `AggregateWithFlush` with INFO "Filesystem watcher ready" (`setup=`); the post-replay re-arm waits for it, then the timer only paces real failures. Periodic runtime pairing every 30 min (`btrfsPairInterval`), skipped while a re-arm is pending, the index is not provably complete, or the watch is not ready; a watch death clears `fullScanOK`. `svcutil.ShutdownBudget` 50 s shared by the folder's shutdown steps (`shutdownWork`); main, model and folder-runner supervisors wait `ShutdownServiceTimeout` 65 s (budget + 10 s snapshot cleanup + 5 s) and log an abandoned service at INFO; 65 + 10 s DB close + 2 s log flush = 77 s < systemd's 90 s. The pairing's staging-snapshot cleanup gets its own bounded context. The barrier re-flushes every 250 ms until its canary arrives. **Effect.** Fail-before/pass-after: `TestBtrfsRearmWaitsForWatchReady` (before: "timer=true ready=false"), `TestBtrfsPeriodicPairing` (before: "periodic pairing did not set a baseline: []"), `TestFolderPathWaitsForShutdownWork` (before: tree returned at 10.10 s with the folder still stopping), `TestShutdownPairingHonoursBudget` (before: "ignored the 300ms shared budget"), `TestWatchBarrierReflushesForLateCanary` (before: "flushes=1, 3.00s"). One stop at 18:39 still overran: the shutdown pairing went silent after its snapshot until the supervisors abandoned the folder at 65 s, cause not yet identified (see the next revision).
- **Revision (boot-diff cost and shutdown observability, 2026-11-26).** **Problem.** (1) Every helper call had a blanket 5 min timeout, the boot diff included. Of 13 boot diffs on yarlung since 11-14 three exceeded it (316.9 s, 566.2 s, >600.4 s) and fell back to full scans of 66 min, 4 h 20 min and over 13 h; diff time had no relation to diff size or baseline age (763 paths 20.8 s, 159,990 paths 34.7 s). ### `db-nocow-auto`

- **Revision (was `nocow-auto-migrate`).** **Problem.** The directory flag alone could only flag *new* files: btrfs silently ignores NOCOW on files with extents, so the pre-existing 9.3 GiB folder DB stayed CoW and every 1 GiB-WAL checkpoint rewrote random pages as fresh extents — the ≈0.8 GiB/min device-write bursts measured while `syncing`. **Principle.** Migration is a pure function of observable state (CoW filesystem ∧ flag unset ∧ free ≥ 1.1× set size): decide deterministically, copy byte-identically, rename atomically; every crash-interrupted mix is consistent because the copies are identical bytes. **Details.** DB + WAL migrate as a set (an empty-WAL gate would defer forever — the pool never checkpoint-removes it at close); copy to sibling temp, fsync, rename all + dir fsync; self-terminating; `STDBNOCOW=0` opts out; off Linux the gate is a stub false (APFS has no NOCOW concept; CoW is free on flash). **Effect.** yarlung's 9.49 GiB folder DB migrated in 22 min one-time on busy spindles (main.db: 154 ms); the 1 GiB-checkpoint-into-CoW bursts are gone — the nine live NOCOW checkpoints captured afterwards showed 2.04× excess writes = pure RAID1 mirroring, zero CoW amplification.
